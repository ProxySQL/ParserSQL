# Curated MySQL compatibility checks

This harness tracks a small, deliberately selected set of MySQL syntax witnesses and known ParserSQL gaps. It does not measure the percentage of the MySQL dialect supported, implement mysqltest/MTR extraction, or establish query-engine execution support.

The five previously tracked witnesses—`JSON_TABLE`, `CREATE TABLE`, `ALTER TABLE`, `CREATE PROCEDURE`, and optimizer hints—now require `CHECKED` outcomes. This closes those particular parse/emission/reparse gaps; it does not establish full support for any of those MySQL feature families.

`JSON_TABLE` retains separate document, path, column-list, column, nested-path, and response nodes. Supported columns include `FOR ORDINALITY`, typed `PATH`, `EXISTS PATH`, and recursive `NESTED PATH ... COLUMNS` with a limit of 128 column-list levels. Both pinned grammars require `PATH` after `NESTED`. Paths use native text literals, including national/charset prefixes and adjacent quoted fragments. `NULL`, `ERROR`, and `DEFAULT` responses preserve `ON EMPTY` and `ON ERROR` in either native order; the reversed order is deprecated by MySQL. DEFAULT uses the native signed-literal production, including numeric, text, temporal, hex, and bit literals. A table alias is required, and an alias-column list is not accepted. The [8.4.8 JSON_TABLE productions](https://github.com/mysql/mysql-server/blob/0896fcd61dec11a0904166911a0126f59daaa1bf/sql/sql_yacc.yy#L12023) and [9.7.2 JSON_TABLE productions](https://github.com/mysql/mysql-server/blob/008e09c2834b98143a8c067d4d225c90953050cf/sql/sql_yacc.yy#L12447) define this bounded grammar coverage. JSON path validity and conversion semantics remain native semantic checks.

MySQL table DDL preserves structured definitions, constraints, options, and ALTER actions. The supported subset includes column types and attributes, generated/default expressions, common keys, CHECK and foreign-key constraints, common table options, and ADD/DROP/MODIFY/CHANGE/RENAME actions. TEMPORARY and IF NOT EXISTS are supported for CREATE TABLE. Shared native type parsing also serves JSON_TABLE columns and procedure parameters; VECTOR is a 9.7 type and is not part of the 8.4 grammar. CREATE TABLE LIKE, query-derived table definitions, partitioning, and specialized index/table options remain outside this bounded implementation. Unknown or incomplete clauses are rejected rather than retained as unvalidated tails. The corpus anchors [8.4.8 CREATE TABLE](https://github.com/mysql/mysql-server/blob/0896fcd61dec11a0904166911a0126f59daaa1bf/sql/sql_yacc.yy#L3217) and [9.7.2 CREATE TABLE](https://github.com/mysql/mysql-server/blob/008e09c2834b98143a8c067d4d225c90953050cf/sql/sql_yacc.yy#L3317), plus the ALTER and definition productions used by each witness.

`CREATE PROCEDURE` preserves typed IN/OUT/INOUT parameters, SQL-language routine characteristics, a single supported query/DML/SET statement or a BEGIN/END body, and nested blocks up to 64 levels. Statement separators inside supported bodies remain part of the procedure AST, including when parsing a batch. This grouping guarantee does not extend to unsupported or malformed routine bodies: the batch parser can stop at an inner semicolon and reports a failed batch. Local and user-variable SET assignments are supported. CREATE DEFINER, procedure IF NOT EXISTS, non-SQL languages, DECLARE, labels, conditionals, loops, cursors, handlers, and scoped/session-configuration SET forms remain unsupported. These broader native constructs are not labeled malformed merely because ParserSQL rejects them. The corpus records [8.4.8 procedure productions](https://github.com/mysql/mysql-server/blob/0896fcd61dec11a0904166911a0126f59daaa1bf/sql/sql_yacc.yy#L17938) and [9.7.2 procedure productions](https://github.com/mysql/mysql-server/blob/008e09c2834b98143a8c067d4d225c90953050cf/sql/sql_yacc.yy#L18697), including parameter, characteristic, and block productions.

Optimizer hints immediately following their supported statement keyword are retained losslessly in a dedicated comment node. This preserves their contents and position during emission; ParserSQL does not interpret or validate the hint language or promise that a native optimizer applies a hint. Unknown hint names can be accepted by MySQL with warnings. Ordinary comments are still outside this hint-preservation guarantee. These additions provide syntax/AST support: local execution and conservative parameterization reject unsupported JSON_TABLE, table DDL, procedure, and hinted-statement semantics.

ParserSQL now preserves MySQL JSON arrows, named/inherited windows, `GROUP_CONCAT` modifiers and separators, and grouping alternatives including `GROUP BY ... WITH ROLLUP` as structured ASTs. Database-qualified column names are retained. The local engine rejects these unsupported semantics rather than executing a simplified interpretation; parameterization remains conservative for JSON arrows and `GROUP_CONCAT`. Empty MySQL SELECT target lists are rejected.

MySQL JSON aggregates use structured ASTs with native argument counts: `JSON_ARRAYAGG` takes one expression and `JSON_OBJECTAGG` takes two. Each argument accepts an explicit `ALL`; `DISTINCT`, a bare star, in-call ordering, and wrong arities are rejected. Both functions preserve optional window clauses. With `IGNORE_SPACE` off, these built-in forms require an adjacent opening parenthesis; spaced or quoted names remain ordinary function calls. The 9.7.2 `JSON_ARRAYAGG` extension preserves `NULL ON NULL` and `ABSENT ON NULL`; neither clause belongs to `JSON_OBJECTAGG`. These clauses are absent from the 8.4.8 production. Native 9.7.2 accepts `NULL ON NULL` but returns unsupported-feature error 1235 for the curated `ABSENT ON NULL` witnesses outside JSON duality views. The [8.4.8 JSON aggregate productions](https://github.com/mysql/mysql-server/blob/0896fcd61dec11a0904166911a0126f59daaa1bf/sql/sql_yacc.yy#L10988) and [9.7.2 JSON aggregate productions](https://github.com/mysql/mysql-server/blob/008e09c2834b98143a8c067d4d225c90953050cf/sql/sql_yacc.yy#L11397) define this bounded coverage. These are syntax/AST guarantees; the local engine rejects the new aggregate nodes, and parameterization remains conservative.

`GROUP BY ROLLUP(...)` and `GROUP BY CUBE(...)` exist in both pinned versions; `GROUP BY GROUPING SETS ((...), ())` is a 9.7.2 addition. These standalone grouping alternatives retain their expression lists and empty grouping sets. Mixed top-level lists such as `id, ROLLUP(n)`, missing per-set parentheses, and combining `ROLLUP(...)` with `WITH ROLLUP` are rejected. The [8.4.8 grouping productions](https://github.com/mysql/mysql-server/blob/0896fcd61dec11a0904166911a0126f59daaa1bf/sql/sql_yacc.yy#L12455) and [9.7.2 grouping productions](https://github.com/mysql/mysql-server/blob/008e09c2834b98143a8c067d4d225c90953050cf/sql/sql_yacc.yy#L12879) distinguish syntax from execution prerequisites: the native fixture accepts ROLLUP, while CUBE and nonempty GROUPING SETS witnesses return secondary-engine error 3889. A row-valued ROLLUP operand is grammar-valid but returns semantic error 1241. Unquoted nested ROLLUP/CUBE calls in grouping expressions are rejected; quoted names remain ordinary function calls and produce server error 1630 on the fixture because no such stored functions exist. ParserSQL preserves these ASTs and rejects unsupported local execution.

MySQL `EXPLAIN` retains options in native order: optional `ANALYZE`, optional `FORMAT = name`, then optional `INTO @variable`. Plain EXPLAIN INTO is present in both pins; ANALYZE INTO is a 9.7.2 addition. Formats and destination names retain their source quoting, including escaped quotes/backticks. Query bodies include WITH, TABLE, and VALUES expressions. Table-description forms emit as DESCRIBE, accept FORMAT as an ordinary table identifier, and preserve hex/bit column-filter literals. The two missing FORMAT-table witnesses return native errors 1146 and 1049, while the four literal-filter witnesses are accepted. Duplicate or reordered options, system-variable destinations, and missing query bodies are rejected. INTO without an explicit format and INTO with TREE remain grammar-valid observations with native semantic errors 6006 and 6007. The [8.4.8 EXPLAIN option productions](https://github.com/mysql/mysql-server/blob/0896fcd61dec11a0904166911a0126f59daaa1bf/sql/sql_yacc.yy#L14034) and [9.7.2 EXPLAIN option productions](https://github.com/mysql/mysql-server/blob/008e09c2834b98143a8c067d4d225c90953050cf/sql/sql_yacc.yy#L14611) define this bounded syntax support. Native EXPLAIN ANALYZE checks execute only SELECT queries on owned fixture connections; these observations do not establish ParserSQL execution support. EXPLAIN FOR CONNECTION and FOR DATABASE remain outside this batch.

MySQL `EXTRACT(unit FROM expr)`, keyword forms of `SUBSTRING`/`SUBSTR`/`MID`, and `MATCH ... AGAINST` have structured ASTs. EXTRACT accepts the twenty native interval keywords, including compound units, and rejects quoted or unknown units. Substring calls retain the alias spelling and support both comma arguments and `FROM ... [FOR ...]`. MATCH preserves qualified column lists, default/natural/boolean modes and query expansion; its optional column-list parentheses are emitted canonically. The search operand enforces the native `bit_expr` precedence boundary, so a comparison must be parenthesized before a search mode. General expression gaps still apply inside these forms: unary `!` operands are accepted by both pinned servers but remain unsupported by ParserSQL. Complete-operand parsing rejects empty tuples, invalid ROW arity, missing grouping/query delimiters, invalid EXISTS bodies and incomplete CASE branches. The local engine rejects these special AST semantics; parameterization remains conservative for the new node kinds. The [8.4.8 special-function productions](https://github.com/mysql/mysql-server/blob/0896fcd61dec11a0904166911a0126f59daaa1bf/sql/sql_yacc.yy#L10661) and [9.7.2 special-function productions](https://github.com/mysql/mysql-server/blob/008e09c2834b98143a8c067d4d225c90953050cf/sql/sql_yacc.yy#L11070), together with the corpus's MATCH, interval, and identifier anchors, define this bounded syntax coverage.

MySQL `CAST(expr AS cast_type)`, both `CONVERT(expr, cast_type)` and `CONVERT(expr USING charset)`, charset-introduced text/hex/bit literals, and expression `COLLATE` retain structured ASTs. Cast types follow the native cast-specific productions rather than general column definitions: numeric, temporal, character/binary, JSON, and spatial targets preserve their accepted modifiers and source spelling. Character targets retain charset and binary attributes. Introducers recognize the shared native charset names (including the `utf8` alias), support intervening whitespace, and retain literal kind. Literal emission preserves MySQL double-quote delimiters, including embedded apostrophes and doubled double quotes, with `ANSI_QUOTES` off. Expression `COLLATE` accepts a simple identifier or quoted name, with native precedence; bare `BINARY`, `DEFAULT`, qualified names, and missing operands are rejected. `CONVERT ... USING` additionally accepts bare `BINARY`. The [8.4.8 cast/conversion productions](https://github.com/mysql/mysql-server/blob/0896fcd61dec11a0904166911a0126f59daaa1bf/sql/sql_yacc.yy#L10425) and [9.7.2 cast/conversion productions](https://github.com/mysql/mysql-server/blob/008e09c2834b98143a8c067d4d225c90953050cf/sql/sql_yacc.yy#L10745), plus the corpus's exact type, literal, charset, and collation anchors, define this bounded grammar coverage. Cast `ARRAY`, `AT LOCAL`, and `AT TIME ZONE` forms remain outside this batch. Native lexical aliases such as `FLOAT4`, `FLOAT8`, and `INT4` are retained. Single field lengths permit native decimal-number tokens; two-part decimal precision and temporal precision use a native integer `NUM` token from 0 through 2147483647. Runtime precision limits remain native semantic checks. These nodes are syntax/AST support: the local engine rejects unsupported semantics, and parameterization remains conservative.

With `IGNORE_SPACE` off, native EXTRACT and substring aliases require `(` immediately after the function name. ParserSQL follows that lexical boundary for these special forms; `MATCH (` remains valid. Spaced comma calls are ordinary function-call syntax and can resolve differently on a native server. This is not general SQL-mode emulation. The [native lexer](https://github.com/mysql/mysql-server/blob/0896fcd61dec11a0904166911a0126f59daaa1bf/sql/sql_lex.cc#L1567) distinguishes adjacent function tokens, and [the function-token table](https://github.com/mysql/mysql-server/blob/0896fcd61dec11a0904166911a0126f59daaa1bf/sql/lex.h#L831) maps `MID` and `SUBSTR` to `SUBSTRING`.

ParserSQL also preserves partition lists, `USE`/`FORCE`/`IGNORE INDEX` or `KEY`, hint scopes and empty `USE INDEX ()`, and `LATERAL` derived SELECTs with required aliases and optional alias-column lists. The local engine rejects these unsupported table-reference semantics. `SELECT` and `UPDATE` place `PARTITION` before the table alias; single-table `DELETE` places it after the alias. LATERAL derived queries include `SELECT`, `TABLE`, and `VALUES ROW(...)` expressions and their set operations.

MySQL query expressions also preserve explicit `TABLE name` and `VALUES ROW(...)` constructors in standalone, compound, derived, LATERAL, scalar, IN, EXISTS, and query-only CTE contexts. `INTERSECT` binds more tightly than `UNION` and `EXCEPT`; explicit parentheses and branch-local ordering/limits are retained. Recursive CTEs retain their keyword and optional column lists. Query locking clauses, including `LOCK IN SHARE MODE`, remain structured. This is parser/AST coverage; the local engine rejects unsupported query forms.

Top-level MySQL `WITH` and `WITH RECURSIVE` also retain structured UPDATE and DELETE main statements, including join/comma UPDATEs, both multi-table DELETE target-list forms, quoted CTE names, partitions, statement options, and single-table ordering/limits. CTE bodies and subqueries remain query-only; DML inside them and a leading `WITH ... INSERT` are rejected. UPDATE assignments require one-, two-, or three-part column names and accept both `=` and `:=` (emitted as `=`), including `DEFAULT` values. UPDATE options follow `LOW_PRIORITY` then `IGNORE`; DELETE options may appear in any order and repeat. The [8.4.8 UPDATE/DELETE productions](https://github.com/mysql/mysql-server/blob/0896fcd61dec11a0904166911a0126f59daaa1bf/sql/sql_yacc.yy#L13389) and [9.7.2 UPDATE/DELETE productions](https://github.com/mysql/mysql-server/blob/008e09c2834b98143a8c067d4d225c90953050cf/sql/sql_yacc.yy#L13945) attach an optional WITH clause to each main statement. Routing metadata identifies the main DML target, including wildcard DELETE targets. JOIN conditions require complete ON/USING operands and retain quoted USING column names. These are parser/AST guarantees; the local engine rejects CTE-prefixed DML.

MySQL INSERT constructors and SET sources retain `AS row_alias` and optional column aliases before `ON DUPLICATE KEY UPDATE`, including quoted names and doubled-backtick escapes. Alias emission separates the row name from its column-list parentheses. With `IGNORE_SPACE` off, native function names such as `COUNT` and `MAX` require this separator when used as unquoted row aliases; adjacent parentheses turn them into function tokens and are rejected. Explicit alias-column parentheses require a nonempty identifier list; the native empty production means that the entire list is omitted. `VALUE` emits canonically as `VALUES`, and `:=` assignment operators emit as `=`. SET and duplicate-key assignments require complete column targets and values, including qualified targets and `DEFAULT`. INSERT also accepts partition lists and query sources containing set operations, parentheses, WITH, TABLE, and `VALUES ROW(...)`. Row aliases belong to INSERT's VALUES/SET source productions; REPLACE and query sources do not accept this suffix. REPLACE also excludes duplicate-key updates. The [8.4.8 INSERT/REPLACE productions](https://github.com/mysql/mysql-server/blob/0896fcd61dec11a0904166911a0126f59daaa1bf/sql/sql_yacc.yy#L13064) and [9.7.2 INSERT/REPLACE productions](https://github.com/mysql/mysql-server/blob/008e09c2834b98143a8c067d4d225c90953050cf/sql/sql_yacc.yy#L13620), with the corpus's constructor, alias-list, and assignment anchors, define these bounded parser/AST guarantees. Parameterization remains conservative for row aliases. Local INSERT execution and direct INSERT planning reject unsupported row aliases, query sources, and partition selection. Native checks use EXPLAIN; they do not establish local-engine execution support.

The native grammar permits empty `VALUES ROW()`, `VALUES ROW(DEFAULT)`, and repeated locking clauses. Both pinned servers return semantic errors 3942, 3943, and 3569 respectively for the curated standalone or overlapping-lock witnesses. These remain `SERVER_ERROR` observations, not syntax rejections, while ParserSQL preserves the grammar-valid ASTs. `TABLE` takes a table identifier and query-level tails; aliases, partitions, index hints, and WHERE clauses directly after its table name are malformed controls. The [8.4.8 query-primary productions](https://github.com/mysql/mysql-server/blob/0896fcd61dec11a0904166911a0126f59daaa1bf/sql/sql_yacc.yy#L9831) and [9.7.2 query-primary productions](https://github.com/mysql/mysql-server/blob/008e09c2834b98143a8c067d4d225c90953050cf/sql/sql_yacc.yy#L10145) include both constructors. The corpus records exact anchors for their rows, subquery contexts, locking, CTEs, and malformed controls.

Table identifiers and aliases use the common 259-word reserved baseline observed in the pinned 8.4.8 and 9.7.2 releases. ParserSQL has no MySQL version setting, so the five 9.7-only reserved additions (`CUBE`, `EXTERNAL`, `LIBRARY`, `QUALIFY`, and `TABLESAMPLE`) remain accepted as names. Strict version-specific identifier rules remain a gap. The INSERT alias function-token check likewise uses the 35 names shared by both pins; the additional 9.7 `JSON_DUALITY_OBJECT` function-token distinction remains outside that common baseline.

Numeric-looking unquoted qualified table names such as `db.123` are valid natively but remain unsupported: the tokenizer reads `.123` as a numeric literal. ParserSQL rejects these forms; earlier behavior could emit an incorrect alias. Lossless parsing of this identifier edge remains a gap.

[The corpus](../tests/mysql_compat/cases.json) contains hand-reduced SQL, intended validity, explicit expected ParserSQL outcomes, and source grammar paths, lines and excerpts for both versions. A grammar anchor identifies related upstream syntax; it does not claim that the reduced query is verbatim upstream test SQL or that source inspection is a native parser oracle. Hand-written controls are identified separately. The runner can verify the source commits and excerpts locally.

Run from the repository root:

```sh
make -B lib
# The CI gate is also available as: make test-mysql-compat
python3 scripts/mysql_compat/build_probe.py --output /tmp/parsersql-mysql-probe
python3 -m unittest discover -s tests/mysql_compat -v
python3 scripts/mysql_compat/run.py --probe /tmp/parsersql-mysql-probe \
  --report /tmp/parsersql-mysql-report.json
```

`build_probe.py` compiles a standalone C++17 executable against the existing `libsqlparser.a`; it does not rebuild that archive. Rebuild the library with `make -B lib` before checking parser changes: the Makefile does not track all header dependencies, so a plain incremental build can leave a stale archive. `CXX` selects the compiler. Keep binaries and generated reports outside the repository.

To also verify the source provenance, add `--source84 /path/to/mysql-8.4.8` and `--source97 /path/to/mysql-9.7.2`. Each checkout must have exactly the pinned HEAD and contain `sql/sql_yacc.yy`; no native MySQL build is required for this check. These are the official source links for the [8.4.8 grammar](https://github.com/mysql/mysql-server/blob/0896fcd61dec11a0904166911a0126f59daaa1bf/sql/sql_yacc.yy) and [9.7.2 grammar](https://github.com/mysql/mysql-server/blob/008e09c2834b98143a8c067d4d225c90953050cf/sql/sql_yacc.yy).

The strict parse gate requires status `OK`, `full_input=true`, and a non-null AST. Failure categories are `ERROR`, `PARTIAL`, `NO_AST`, and `TRAILING_INPUT`. `NO_AST` takes precedence over trailing input; the report retains the raw flags and remaining SQL so neither fact is lost. In particular, classification-only DDL must not count as structured parsing.

Complete parses have their emitted SQL reparsed through the same strict gate. The emitted text must stabilize after that reparse. Positive controls also specify exact expected SQL, including JSON `->` and `->>` operators. These checks can expose dropped or changed syntax even when the altered SQL still parses. They are bounded emission checks, not a proof of AST or execution equivalence. `CHECKED` means only that these checks passed. Optimizer-hint witnesses require their comment text to survive emission exactly.

Malformed controls are handled separately: a complete AST is `MALFORMED_ACCEPTED`, even when emission changes. The `SELECT FROM` and malformed JSON-arrow controls require rejection. A rejection is `REJECTED`; the original record still identifies whether it was an error, incomplete input, or a missing AST.

Every fixture freezes one exact expected outcome. Known gaps do not make arbitrary failures acceptable. Both regression and unexpected improvement cause exit status 1, so a fixed gap must be reviewed and explicitly promoted in the corpus. When promoting, add an independently derived `expected_sql`, set `known_gap=false`, and require `CHECKED`. Harness/transport/source errors return 2. Exit status 0 means the expected baseline matched, including its documented known gaps.

The 385-case curated baseline has 192 `CHECKED` witnesses and 193 `REJECTED` malformed controls, with no remaining `known_gap` records. All five previously tracked gaps are promoted. Source verification checks 465 exact grammar anchors per pinned release. These counts describe this selected corpus only, not overall dialect coverage.

The JSON report includes all original and reparsed records, source verification counts, pinned revisions, SQL-mode metadata, and SHA-256 hashes of the corpus and probe. Counts apply only to these witnesses. The probe uses hex-line input and hex fields in its TSV response, preserving tabs, newlines and embedded NUL bytes. It emits while both the input string and parser arena are alive; Python reparses owned copies in a second probe invocation.

The default corpus oracle state is **NOT VERIFIED**. Its intended `sql_mode` is the empty string; ParserSQL accepts no mode configuration here and the harness does not apply or emulate MySQL session modes. A native server check requires its exact version, actual session mode, schema fixtures, SQL sent, and result/error code. Missing tables, mode-dependent errors, or unsupported runtime features must not be relabeled as syntax rejection. Without native options the harness does not connect to a database. An optional native run uses an explicit absolute socket path to an already-running, isolated server:

```sh
python3 scripts/mysql_compat/run.py --probe /tmp/parsersql-mysql-probe \
  --native-socket /absolute/path/to/isolated-mysql.sock \
  --mysql-client /absolute/path/to/mysql \
  --report /tmp/parsersql-mysql-native.json
```

The client uses `--no-defaults`, the supplied socket, and `root` unless `--native-user` is specified. There is no host discovery or automatic connection. Use an isolated test server: this option explicitly creates a uniquely named `parsersql_compat_<uuid>` database, installs the small fixture in [native.py](../scripts/mysql_compat/native.py), and drops only that owned database in cleanup. Each DDL/procedure case additionally creates its own uniquely named schema, installs only its explicitly recorded `native_fixture_sql` when needed, and drops that schema after the observation. An ALTER witness therefore gets a clean table without conflicting with the shared query fixture. Cleanup also runs after statement rejection or fixture failure; a failed CREATE DATABASE never grants ownership for DROP. The partition witnesses use a separate `pt` table with populated `p0` and `p1` range partitions; `t` retains its fulltext index for the existing search witness. The supplied user needs permission to create/drop that database and its tables. The helper requires server version 8.4.8 or 9.7.2, records the exact reported version and session SQL mode, and reapplies that mode for each query. It does not assert that the native mode equals the corpus's empty intended mode.

Each curated case explicitly chooses direct query execution, `EXPLAIN` for DML (including CTE-prefixed DML), isolated DDL/procedure creation, or no native action. The `ddl` action uses the mysql client's DELIMITER command with a marker absent from the witness, so internal procedure semicolons are sent in one statement. Per-case reports retain the schema, fixture SQL, exact client input, and cleanup result. Procedure creation is observed; procedure bodies are not called or executed by this action. These are query-execution or EXPLAIN observations, not access to MySQL's raw parser. Returned row values are evidence only; they are not compared with ParserSQL execution. The standard corpus run submits original SQL only and does not claim semantic round-trip validation.

Native results are stored separately in `native_oracle`: `ACCEPTED`, `SYNTAX_REJECTED` (1064/1149), `SERVER_ERROR`, `CLIENT_ERROR`, or **NOT VERIFIED**. For example, a derived table missing its required alias returns error 1248, and the corresponding JSON_TABLE witness returns 3667; these remain server errors, even though the corpus requires ParserSQL to reject those inputs. Accepted invalid controls and syntax-rejected valid controls count as expectation mismatches, using per-version validity when specified. Server errors remain explicitly unresolved; client errors return status 2. Thus exit status 0 still does not mean all native cases were verified. The default corpus metadata remains **NOT VERIFIED**, while the optional report describes the actual native observations.

Native checks of all 385 witnesses under `ONLY_FULL_GROUP_BY,STRICT_TRANS_TABLES,NO_ZERO_IN_DATE,NO_ZERO_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION` found no intended-validity mismatches. MySQL 8.4.8 accepted 170, syntax-rejected 198, and returned 17 server errors; MySQL 9.7.2 accepted 175, syntax-rejected 188, and returned 22 server errors. Every case had a native action, including DDL and procedure creation; no cases were skipped, and all owned schemas were cleaned up. Semantic errors remain unresolved observations, including missing aliases, unsupported runtime features, engine prerequisites, and error 1235 for the grammar-valid procedure parameter `COLLATE BINARY` witness in both releases. These must not be relabeled as syntax rejection. Reports are intentionally kept outside the repository; rerun each isolated socket to reproduce current observations. Separate native runs also submitted all 192 valid emitted witnesses to each pinned server. Every emitted statement retained the original observation state and error code. This is a bounded additional emission check, not proof of AST, optimizer, result-value, or execution equivalence.

The corpus is deliberately selected and is not a representative workload. It includes shared and explicitly version-specific witnesses; this does not imply identical dialects in 8.4.8 and 9.7.2. The version-specific entries record `applicability`, source productions for both versions, `native_validity` per version, and observed native outcomes. Their generic `validity=valid` denotes the 9.7.2 grammar target. The native helper selects the intended validity using the actual server version, so an expected 8.4.8 syntax rejection is not treated as a corpus error. Stored native observations are context, not substitutes for a current run. These version-specific query additions now pass ParserSQL parse/emission/reparse checks; native runtime restrictions remain separately reported. The pinned 9.7.2 grammar contains the corresponding [VECTOR type](https://github.com/mysql/mysql-server/blob/008e09c2834b98143a8c067d4d225c90953050cf/sql/sql_yacc.yy#L7240), [view clause](https://github.com/mysql/mysql-server/blob/008e09c2834b98143a8c067d4d225c90953050cf/sql/sql_yacc.yy#L18217), [EXPLAIN options](https://github.com/mysql/mysql-server/blob/008e09c2834b98143a8c067d4d225c90953050cf/sql/sql_yacc.yy#L14612), [JSON aggregate clause](https://github.com/mysql/mysql-server/blob/008e09c2834b98143a8c067d4d225c90953050cf/sql/sql_yacc.yy#L11397), and [GROUPING SETS](https://github.com/mysql/mysql-server/blob/008e09c2834b98143a8c067d4d225c90953050cf/sql/sql_yacc.yy#L12893). Grammar presence and successful execution are different observations: unsupported features and missing engine prerequisites remain unresolved, not accepted by the native helper. Likewise, window `GROUPS` and `EXCLUDE` appear in upstream grammar but returned unsupported-feature errors in both versions; this batch does not claim to implement them.
